# Validation scope

The current local source-tree checks use CPython 3.12.15, SQLite through Python's standard driver, Linux aarch64, Node.js 24.19.0 and TypeScript 6.0.2. The earlier source snapshot was checked on CPython 3.12.14 and Linux x86_64; the current changes have not been rerun on x86_64. The two Python locks pin the same dependency versions with platform-specific wheel hashes. The checks use actual FastAPI/Pydantic 2/SQLAlchemy 2/Alembic dependencies.

| --- | --- |

| Crash consistency | Termination after Project, receipt or outbox insertion, before commit, and after commit with response lost; reopen, retry, integrity and FK checks |
| Race behavior | Concurrent duplicate requests create one Project/receipt/event; a waiting command sees committed grant revocation or policy revision change |

The current Starlette test adapter emits a deprecation notice for its supported `httpx` integration. Tests still exercise the real adapter; migration to its replacement client remains a development dependency update, not a hidden test skip.

The initial migration is unshipped and was corrected during local review. The additive `0002_browser_sessions` migration upgrades that corrected foundation without creating identities or rewriting existing Project records. It does not repair databases created from the older, uncorrected development snapshot. Existing retained data from that older schema needs a separately validated migration; recreating disposable test databases is not a retained-data upgrade strategy.

Not run or provided: application wheel/build/install, installer, container/ASGI deployment, browser or native client qualification, production ceremony provisioning, live provider/MCP/terminal calls, Raspberry Pi qualification, load/performance budgets, encrypted backup/restore, release/signing/update flows, external outbox delivery or public compatibility guarantees. These limits prevent this slice being treated as an operational release. Passkey tests use synthetic authenticators with real signatures and the maintained verifier through the ASGI test adapter. Session tests also use synthetic trusted authentication evidence. Neither substitutes for browser virtual-authenticator acceptance. They do not qualify recovery from an older backup, deployment-incarnation fencing, protected confirmation, security-event delivery or WebSocket authorization.

The Python license inventory comes from installed distribution metadata and SHA-256 of downloaded wheels. `tools/lock_dependencies.py work/wheels` regenerates the default lock and inventory after an intentional dependency update; obtain only the exact installed wheels for the current platform before running it. On aarch64, preserve the x86_64 files with `tools/lock_dependencies.py work/wheels --lock-file requirements-linux-aarch64.lock --inventory-file dependency-inventory-linux-aarch64.json`. Run the tool with the intended environment's Python. It does not decide legal compatibility, collect complete distribution notices or authenticate upstream provenance. Inspect dependency licenses and notices before distributing bundled software.


Passkey service policy requires explicit configuration. The available standard profile uses 300-second ceremonies, 900-second enrollment, five failed verifications per challenge and per rolling 300-second credential/account passkey-family window, and 30 starts per rolling 300-second source window. Selecting this profile remains explicit. Canonical credential and account-family budgets span login, step-up, renewed challenges and sources; unknown credentials also share a source failure budget. Only admitted failed verifications append failure events. Throttled requests do not extend their expiry, and successful authentication does not clear retained history. Source identity comes from the transport peer, not forwarded headers. Deployments behind a proxy need an independently validated trusted-source integration; shared proxy or NAT peers share source limits. Expired events are pruned during admitted budget checks. This bounds retained history by the active windows and admitted traffic, not by a globally fixed row cap or a demonstrated distributed-load budget. Trusted local administration can prepare an enrollment secret; there is no public preparation route or supplied secret-store provisioning workflow. Successful bootstrap atomically establishes the Owner, labeled credential and session. Durable challenges bind purpose and session, count failed verification attempts, and remain unusable after observed expiry and clock rollback. A process exit before commit leaves no partial Owner or session; a committed credential permits a new login if the original response is lost. Counter regression is denied when either stored or received counter is nonzero; authenticators that consistently use zero remain supported.

Multiple-passkey management, protected confirmation, password/TOTP/email authentication, recovery, federation and identity linking are not implemented by these routes. Those remaining identity flows are not qualified by bootstrap/login/step-up checks. The current Owner binding rejects ordinary demotion, disabling, deletion and reassignment; dedicated recovery must preserve the separate recovery contract.

The verifier is `fido2==2.2.1`. Its full core BSD notice and bundled MPL/Apache notice wording are retained in `fido2-notices.txt`; one trailing space is normalized. `cryptography`, `cffi` and `pycparser` are pinned in both platform inventories. Application code delegates WebAuthn cryptographic verification to the verifier; test authenticators sign synthetic challenges locally.

The rolling-budget migration preserves legacy source counts as weighted events at their stored last observation, without inventing individual timestamps. Their expiry is bound on first explicitly configured use to one source window after that observation. This can conservatively deny an additional interval of at most one configured window; migration never restores an exhausted budget merely by replacing the schema. Legacy rows remain retained. The first explicit policy is durably bound; subsequent mismatched instances fail without changing the binding or retained event expiry. Online policy reconfiguration is unsupported and needs an explicit, separately validated administrative migration. Repeated matching configuration does not extend denial. Clock observations and budgets survive restart. These checks do not qualify accessibility, shared-network fairness, distributed denial resistance or retry integration for authentication methods not yet implemented.

Explicitly configured passkey HTTP routes also reserve a rejected-input source slot before reading the body. This separate budget uses the configured source count and window; valid finishes do not count as new starts. Body-size, DTO, JSON and service-classified invalid-ceremony rejections retain the admission timestamp. Successful responses, credential-verification denials, downstream throttles and server errors release the slot. At admission, unexpired, unreleased reservations cannot exceed the configured source budget, and no database transaction spans a body read or handler execution. A disconnected or interrupted request conservatively retains its reservation until that existing window expires; it cannot extend the timestamp. Missing peer attribution uses one shared fallback bucket; untrusted forwarding headers cannot choose a new source. Explicitly configured trusted proxy peers may supply the client address. This enforces a rolling-window budget for rejected input and unexpired pending reservations; completed successful requests release capacity. A body read or handler can outlive its reservation, so this does not bound total in-flight requests or request lifetime. Request-lifetime and aggregate-capacity controls and qualification remain required work, alongside load, shared-network fairness, slow-user accessibility and proxy qualification.

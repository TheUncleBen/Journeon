# Local Project instruction operations

Instruction APIs require an explicit runtime `instructions` configuration. It names absolute local roots, their Environment or exact Project role, configuration revisions, and finite positive `protected_request_seconds` and `protected_preview_seconds`. Those two validity values have no defaults. Existing strong-authentication and session deadlines still apply. Configuration does not register roots, install assets, grant access or approve a change.

The authenticated API can inspect and admit configured roots, register the running package's CORE and NAVIGATION assets, and configure Project instruction policy through the closed protected-operation prepare, preview and confirm endpoints. The first-party `/instructions/authenticate` page provides passkey sign-in and step-up. After preparing a request, open `/instructions/confirmation/<request_id>` to inspect the server-rendered stored effect and explicitly confirm or cancel it. Only the nonsecret request reference belongs in the URL; session, CSRF and preview tokens do not. The page supports keyboard decisions, focused result/error announcements, reflow and light/dark presentation, and denies framing with no-store and no-referrer controls. Authentication refresh invalidates old session-bound requests; prepare a new request afterward. The authenticated page can report current expiry or authorization failure without applying the effect. Confirmation uses the current official browser session, recent strong authentication, exact stored operands and a short-lived single-use preview nonce. A caller-supplied approval flag, absolute path or arbitrary command is not an operation. Root admission binds directory and Git worktree identity; changing or revoking that binding invalidates dependent operations.

Candidate package registration has `DEVELOPMENT_CANDIDATE` provenance. A separate installed-release path verifies an Ed25519 signature using explicitly configured trust, matching installed source and instruction manifests, artifact hash, version, channel, platform, schema and service-produced current health, compatibility and paired database/external-tree backup evidence. Verification creates a new private directory beside the configured `backup_path`, using that name plus a unique `.qualification-` suffix. It never overwrites the configured file or an existing backup. The backup contains the canonical database and exact accepted instruction documents, bound to roots, policy, revisions and terminal journal state. Unresolved publication, unknown edited bytes, stale health, changed state or mismatched backup bytes deny installation. Install admission observes signed artifacts and paired backup bytes before its final current root/tree health check, fences backup identity and change times across those checks, and rechecks the observed database state (including publication generations) in the mutation transaction. File copying and long filesystem observations remain outside that transaction. Unmanaged filesystem writes after the last observation remain a race: filesystem and SQLite updates are not atomic. The installed renderer scenarios execute during qualification; they do not qualify model or native behavior. Backups remain retained without automatic pruning. Restore requires separate authorized reconciliation and must preserve current revocations; verification never restores automatically. The service does not download software, provide an official signing key, promote a local candidate to an official release, or implement an updater. A disposable qualification key establishes only that qualification authority. Protected assets cannot be uploaded through Profile, Bot or Project writers.

Project commands require exact Project instruction capabilities. Owner configuration authority for global operations does not substitute for Project grants. Binding preview describes the proposed ownership and tree difference without accepting content. Environment-owned trees live under `instructions/projects/<project_id>/` in the admitted Environment root. Project-owned trees live under `.journeon/instructions/` in the admitted Project root. Ownership transfer preserves accepted content and history and switches one canonical binding; old files are retained. New Projects receive only the narrow policy for service-generated INDEX normalization that preserves all authorized targets and mandatory fragments. Other edits require a category explicitly named in protected policy configuration. Legacy Projects receive no invented roots or policy; an unconfigured policy retains candidates and denies acceptance.

Proposals retain exact base revisions and hashes, author, reason, source references, diff and measurements. INDEX.md is mandatory. Reads and rendering select INDEX plus explicitly required fragments, while separate authorized document and history reads address retained revisions. Local links cannot cross the tree boundary. Selected text uses the existing closed template grammar and cannot contain undeclared variables. Unknown eval suites are rejected. Associated deterministic scenarios exercise rendering, literal variable boundaries and scope checks; they do not establish model behavior or native execution isolation.

Explicit policy controls independent review and exact confirmation. Reviews are immutable, attributed to a current authorized Principal, and cannot be authored by the candidate author. Open findings require a corrected candidate. Acceptance checks current candidate, binding, policy, review and executed eval evidence. Restore creates a new candidate under current policy. Immutable bundle provenance retains the accepted installation manifest and Project tree revision; authorized historical retries do not become newly installed versions. Missing Task, Skill or workflow inputs remain unavailable.

Publication uses a durable journal and one local writer per Project. Staging, Git subset checkpoints and file replacements occur outside SQLite transactions. Checkpoints leave the user's Git index and unrelated files untouched and never create commits or run hooks. Each effect rechecks current authority and exact preimages. Interrupted or externally modified trees remain unresolved; accepted revision, receipt and event advance only after the target bytes agree. Retrying the same admitted operation reconciles known partial writes under its original current authority. A current Owner with exact Project rights can inspect the pending recovery operands and use the closed `project.instructions.recover.v1` protected effect with fresh exact consent. Recovery preserves the original journal, initiating identity, receipt and event identity; it does not renew the expired approval. The explicit `FINISH_TARGET` choice requires the same target, generation, base revision and policy. The explicit `RESTORE_BASE` choice restores only recorded preimages under fresh current authorization, preserves accepted history, clears the pending publication and records an `ABANDONED` receipt/event for the original operation. It supports resolution after a policy change without accepting the stale target. Both choices recheck admitted roots and current rights before effects and finalization. A revoked root first requires a new inspect/admit confirmation. Recovery inspection then supplies the current root revisions, and fresh recovery consent can rebind the pending operation only when the original directory, configured path, role, configuration revision and Git identity still match. It preserves original operation operands and never restores old approval. A substituted root or unknown bytes remain held: reconcile external state to the recorded identity and exact base/target bytes before retrying. Neither recovery choice grants authority over a different root or overwrites unknown edits. Unknown edits are preserved. This does not make a filesystem tree atomically visible to an unmanaged process.

AGENTS.md, CLAUDE.md and GEMINI.md projections are derived views. Preview and check report desired and observed hashes. Materialization is journaled, refuses unmanaged files, and requires the expected observed hash. Drift in an owned disposable projection can be regenerated only at that exact observation; user changes are not silently overwritten. Writing a projection does not prove a native harness loaded it.

HTTP commands retain the existing 65,536-byte body limit. Individual documents and selected rendering are bounded to 65,536 UTF-8 bytes; the service tree is bounded to 256 documents and 4 MiB. These are implementation bounds, not token budgets or risk policy. Candidate metrics report bytes, growth and repeated nonblank lines. No retention or automatic pruning policy is introduced.

Runtime startup exposes local dependency state for explicit configuration, installed registration and unresolved publication through application state. Startup does not migrate, approve, install or repair instruction state. The generated TypeScript client transports the actual APIs; a full editor, native adoption, genuine Skill production inputs, live model qualification and an official signed release remain separate dependencies.

Schema `0009_instruction_scope` upgrades existing `0008_project_instructions` stores while retaining receipt/event rows, indexes, triggers and the event sequence ceiling. Invalid retained Project scope causes migration to fail rather than inventing authority. Fresh installs also enforce explicit non-null Project scope. Terminal abandoned publications do not appear as unresolved startup work.

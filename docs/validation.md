# Validation scope

The current local source-tree checks use CPython 3.12.15, SQLite through Python's standard driver, Linux aarch64, Node.js 24.19.0 and TypeScript 6.0.2. The earlier source snapshot was checked on CPython 3.12.14 and Linux x86_64; the current changes have not been rerun on x86_64. The two Python locks pin the same dependency versions with platform-specific wheel hashes. The checks use actual FastAPI/Pydantic 2/SQLAlchemy 2/Alembic dependencies.

| Check | Evidence and boundary |
| --- | --- |
| Python tests | Automated tests; temporary file DBs, independent connections and real subprocess termination |
| Crash consistency | Termination after Project, receipt or outbox insertion, before commit, and after commit with response lost; reopen, retry, integrity and FK checks |
| Race behavior | Concurrent duplicate requests create one Project/receipt/event; a waiting command sees committed grant revocation or policy revision change |
| Authority | Current Owner/epoch, exact grants, receipt-only access, revoked replay, separate creation/receipt authority, actor-bound receipts and no implicit share grants. Lookup and retry deny revoked, expired or mismatched grants before decoding receipt JSON; a different current Owner cannot distinguish a damaged receipt from a missing one. |
| Persisted-state validation | Every canonical Boolean has a checked database domain; raw non-Boolean writes and a second Owner using `enabled=2` fail. Malformed provider policies, damaged receipt JSON and mismatched receipt operation/Project identities return sanitized dependency errors without creating or rewriting records. |
| API | Default auth denial despite forged headers; explicit HTTPS-origin session binding rejects missing/wrong CSRF and hostile origins. Explicitly configured passkey routes verify registration, passwordless login and session-bound step-up with a maintained WebAuthn verifier. Unconfigured routes deny activation. Strict DTOs, stable sanitized errors and bounded chunked bodies remain enforced. |
| Migrations | Explicit empty-file upgrade, additive session migration preserving existing Owner/Project records, additive passkey migration retaining an existing Owner, session and grant; repeatable upgrade, model/schema comparison, no implicit bootstrap identities and rejection of unknown/missing migration heads |
| Contracts | Checked-in OpenAPI/JSON schemas/client match current generation; strict TypeScript compile and synthetic fetch transport/error tests. The API and generated OpenAPI read the version from `pyproject.toml`; a metadata-change regression prevents drift. |
| Sessions | Hashed opaque tokens, finite independent deadlines, non-sliding polling, current principal epochs, rotation and rollback, own/Owner revocation and inventory, restart persistence, clock rollback denial across rejected transactions and restart, and expiration at final Project commit. Revoked sessions cannot access retries or receipts. |
| Static checks | Ruff lint/format and strict mypy for production code and tools |
| Dependency reproducibility | The aarch64 SHA-256 lock installs offline from downloaded wheels into a separate empty venv; `pip check` passes. Both locks include the same four added runtime dependency versions with platform-specific hashes; x86_64 wheels were downloaded and hashed but not executed. |
| Advisory checks | Earlier snapshot: 30 Python distributions, zero skips and zero reported advisories using pip-audit 2.10.1; npm lock audit reported zero vulnerabilities. The passkey verifier and its dependency additions have not been checked against advisory services; earlier results are point-in-time evidence, not a security certification. |

The current Starlette test adapter emits a deprecation notice for its supported `httpx` integration. Tests still exercise the real adapter; migration to its replacement client remains a development dependency update, not a hidden test skip.

The initial migration is unshipped and was corrected during local review. The additive `0002_browser_sessions` migration upgrades that corrected foundation without creating identities or rewriting existing Project records. It does not repair databases created from the older, uncorrected development snapshot. Existing retained data from that older schema needs a separately validated migration; recreating disposable test databases is not a retained-data upgrade strategy.

Not run or provided: application wheel/build/install, installer, container/ASGI deployment, browser or native client qualification, production ceremony provisioning, live provider/MCP/terminal calls, Raspberry Pi qualification, load/performance budgets, encrypted backup/restore, release/signing/update flows, external outbox delivery or public compatibility guarantees. These limits prevent this slice being treated as an operational release. Passkey tests use synthetic authenticators with real signatures and the maintained verifier through the ASGI test adapter. Session tests also use synthetic trusted authentication evidence. Neither substitutes for browser virtual-authenticator acceptance. They do not qualify recovery from an older backup, deployment-incarnation fencing, protected confirmation, security-event delivery or WebSocket authorization.

The Python license inventory comes from installed distribution metadata and SHA-256 of downloaded wheels. `tools/lock_dependencies.py work/wheels` regenerates the default lock and inventory after an intentional dependency update; obtain only the exact installed wheels for the current platform before running it. On aarch64, preserve the x86_64 files with `tools/lock_dependencies.py work/wheels --lock-file requirements-linux-aarch64.lock --inventory-file dependency-inventory-linux-aarch64.json`. Run the tool with the intended environment's Python. It does not decide legal compatibility, collect complete distribution notices or authenticate upstream provenance. Inspect dependency licenses and notices before distributing bundled software.


Passkey service policy requires explicit ceremony/enrollment lifetimes, attempt limits and start-rate limits. No shipping values are supplied by this implementation. Its current source limiter uses a fixed window and its verification attempts are per challenge; canonical credential/account-family rolling budgets are not implemented. This configuration mechanism does not qualify the complete operational retry policy. Trusted local administration can prepare an enrollment secret; there is no public preparation route or supplied secret-store provisioning workflow. Successful bootstrap atomically establishes the Owner, labeled credential and session. Durable challenges bind purpose and session, count failed verification attempts, and remain unusable after observed expiry and clock rollback. A process exit before commit leaves no partial Owner or session; a committed credential permits a new login if the original response is lost. Counter regression is denied when either stored or received counter is nonzero; authenticators that consistently use zero remain supported.

Multiple-passkey management, protected confirmation, password/TOTP/email authentication, recovery, federation and identity linking are not implemented by these routes. Those remaining identity flows are not qualified by bootstrap/login/step-up checks. The current Owner binding rejects ordinary demotion, disabling, deletion and reassignment; dedicated recovery must preserve the separate recovery contract.

The verifier is `fido2==2.2.1`. Its core BSD notice and bundled MPL/Apache notices are retained verbatim in `fido2-notices.txt`. `cryptography`, `cffi` and `pycparser` are pinned in both platform inventories. Application code delegates WebAuthn cryptographic verification to the verifier; test authenticators sign synthetic challenges locally.
